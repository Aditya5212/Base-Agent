# Base Agent project audit · 18 November 2026

**Decision.** Close the workflow reliability gaps below and verify them on disposable PostgreSQL before starting the Versioning Foundation. The most important failure is visible to anyone polling a run. After a broker outage exhausts dispatch retries, the API can keep reporting `PENDING` indefinitely.

**Scope and evidence.** This time-boxed review examined the clean `main` checkout at `ef8ff48`, including the latest recovery commit. It sampled agent execution, thread-scoped retrieval, workflow validation, run creation and continuation, tool calls, worker leases, migrations, recovery tests, TODO.md and Vision_and_Roadmap.md. Findings below come from tracing production code. Live LLM, object storage, broker and database behavior were outside this run.

## Findings and acceptance checks

| Priority | Finding and user impact | Change and proof of completion |
|---|---|---|
| High | **Exhausted dispatch leaves a run pending.** In [workflow_service.py](app/services/workflow_service.py), `retry_pending_dispatches` excludes rows after five attempts by default. Failed enqueue updates the dispatch alone. The stale-run sweeper selects only `RUNNING` runs, and the admin retry endpoint uses the same cap. Both initial execution and queued resume can stall. | On exhaustion, atomically transition a still-pending run to a visible failure, record the reason and emit an event. Test five broker failures, verify the polling response, and verify that cancellation or a concurrent successful claim is preserved. |
| High | **A setup failure can leave a heartbeat renewing an abandoned run.** In `execute_claimed_run`, the heartbeat starts before the dispatch payload query, detach and rollback. An exception in that interval bypasses the cleanup block. If the independent heartbeat connection works, the sweeper keeps seeing a valid lease although no graph is executing. See [worker lifecycle](app/services/workflow_service.py). | Put setup under the heartbeat cleanup block or start the heartbeat after setup. Inject a dispatch-read failure and verify the heartbeat stops and the run becomes recoverable. |
| High for side-effecting tools | **Within-attempt retries can repeat an external action.** The [tool call node](app/services/workflow/nodes/tool_call.py) retries any exception when retries are enabled. An HTTP service can perform a write and lose its response. A stable key helps only when the recipient honors it. The persisted invocation protects later graph replay, while the immediate retry occurs inside that invocation. | Permit automatic retries for read-only operations or an explicitly idempotent integration. Preserve an ambiguous write outcome for reconciliation. Test a fake recipient that records a write then times out and assert it receives one call. |
| Medium | **A workflow research tool misses thread documents.** The [tool call node](app/services/workflow/nodes/tool_call.py) builds the RAG tool map with only `user_id`. The [tool factory](app/services/rag_tools.py) accepts a thread ID, and the [retrieve node](app/services/workflow/nodes/retrieve.py) already distinguishes a conversation thread from a generated workflow-run ID. A workflow can therefore find a thread document through one node and miss it through the other. | Share the effective-thread resolution. Test the same lookup through both node types with a document in the active thread, another thread and global scope. Include a run with no conversation thread. |

## Next steps in order

1. **Establish a live baseline and fix the reported paths.** Set `TEST_DATABASE_URL` to a disposable PostgreSQL database with pgvector, then run `.venv/Scripts/python.exe -m pytest --run-integration -q tests/integration/test_workflow_execution_recovery.py`. The fixture runs migrations. Check existing data for duplicate tool occurrences before applying the [new unique constraint](alembic/versions/20261118_0001_workflow_continuations.py) to a populated database. Add the regression cases above as each fix lands.
2. **Close Phase 2 with an API-to-worker smoke test.** Run the full integration suite against the disposable database. Start an API and Taskiq worker using the same test environment, queue a two-step workflow, pause it at a boundary, resume it, and check the final output and ordered events. Repeat with a broker interruption. The queue-recovery integration test mocks broker enqueue, so a real delivery adds distinct evidence.
3. **Start Phase 3 with one demonstrable versioning feature.** Pin one dynamic tool revision in a workflow run. Pause the workflow before the tool, edit its draft, then resume and verify the original revision executed. This builds on existing graph snapshots and addresses the current runtime lookup by tool name. Extend the same model to agents and schemas before building history, diff and rollback screens.
